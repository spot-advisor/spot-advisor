# Spot Advisor 2.4 plan

Keep the one-turn, tool-free advisor. Build the first candidate around a narrow outcome: an executor can obtain a judgment on the submitted file against the user's current acceptance conditions, apply it and verify delivery. The [diagnostic report](spot-advisor-2.4-findings.md) identifies where that chain currently breaks.

### Confirmation design

1. Have a second author sample previously unseen tasks and write the acceptable terminal states independently of candidate outputs. Include at least one case from a different artifact family for each observed failure. Freeze task IDs, cases, allowable abstentions, budgets, assignment seed, data exclusions and primary contrast before model runs. Separate a representative workload from the deliberately enriched defect screen.
2. Randomize within each task between **local-only**, **shipped 2.3**, and **candidate 2.4**. For tasks with multiple eligible consultation points, include a **random timing** arm matched to a prespecified consultation budget calibrated on development data. This asks whether the trigger adds value beyond making advice available. Keep the executor, reviewer, tools, wall-clock limit and grading image fixed across applicable arms. Grade the submitted bytes or final external state while blinded to arm. [Methodological basis](wiki/001-evaluating-selective-consultation.md)
3. Use verified delivery by deadline on all assigned tasks as the primary operational outcome. If the scientific claim is better rule-following, preregister its separate paired endpoint of timely correct action plus independent delivery. Report disagreement with partial-credit graders, justified abstention, incorrect acceptance, refusal on valid work, local declines, actual dispatches, subsequent application, time and provider-specific usage. Missing receipts stay identified. Treat repeated runs and translations as clustered within a task.
4. Specify the claim and compute its sample size from assumed paired discordance. As an illustration, the [existing paired power calculation](spot-advisor-2.3-rule-results.md) requires 168 independent pairs for a 10-point benefit under its particular discordance assumptions. A multilingual interaction or lower false-approval target needs a different design. To make a separate claim of a false-approval rate below 5%, even zero errors needs at least 59 independently sampled defective tasks for a one-sided 95% exact bound. Four repeated diagnostic failures belong in the regression suite and cannot establish a field rate.

### Proposed decision gates

These are proposed thresholds for the next preregistration. The present diagnostics have not validated a candidate against them.

- **Delivery correctness.** All known defective, missing-criterion, stale-revision and valid fully specified regression cases receive their expected disposition. On the fresh defect sample, the one-sided upper confidence bound on mistaken approval must be below 5%. On sufficient valid evidence, target at least 90% acceptance and report its interval. Publish both denominators.
- **Benefit.** For an improved rule-following claim against shipped 2.3, target a paired gain of at least 10 percentage points with a positive lower confidence bound on the prespecified endpoint. Report terminal delivery and consultation rate separately. If the study supports only better form admission, ship and describe that narrower result independently of a trigger change.
- **Economy.** For a cheaper-workflow claim, target at least 10% lower cost per verified delivery with a prespecified upper ratio bound of 0.90 and comparable terminal success. Price executor and advisor input, cached input and output separately under a declared pricing model. Report raw tokens and unknown coverage even where dollar attribution is unavailable. Measure native host discovery as well as full-prompt injection.
- **Compatibility.** Recheck both round limits, stale-evidence rejection and no-dispatch previews. Test every advertised transport and the exact install path before including it in a release claim. Scope evidence coverage checks to delivery decisions and preserve the inexpensive path for routine work.

The first implementation should pair requirement coverage and named provenance in one prototype. A correct revision ID can otherwise make an incompletely specified task look ready to ship. Run the existing two-family regression immediately and ask independent authors for new cases before refining wording on any held-out data.
