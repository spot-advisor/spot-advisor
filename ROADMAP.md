# Spot Advisor roadmap

## Spot Advisor 2.4 research and planning

The [diagnostic findings](docs/spot-advisor-2.4-findings.md) trace failures through question admission, evidence selection and final artifact review. The [2.4 plan](docs/spot-advisor-2.4-plan.md) prioritizes acceptance-condition coverage and evidence provenance, followed by bilingual recovery, installation diagnostics and a held-out test of consultation timing.

## Spot Advisor 2.2 research and planning

The [2.1 pilot](docs/spot-advisor-2.1-roadmap.md) established that the consultation and evaluation workflows can run. The question for 2.2 is when a developer gets a better outcome by asking for one checkable next step.

### Release and research decisions

Use one frontier turn when an unresolved decision or a capability gap, such as visual hierarchy, can change an action the executor can verify. ### Six dimensions for comparing advisor workflows

Choose peers for three distinct strengths. [Claude Advisor](https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool) integrates the consultation into model execution. [second-opinion](https://github.com/jensvanbellen/second-opinion) performs an independent repository review. [PAL MCP](https://github.com/BeehiveInnovations/pal-mcp-server/blob/main/docs/advanced-usage.md) offers configurable, deeper multi-model analysis. The matrix describes documented behavior. The same-case benchmark will supply quantitative results.

| Dimension | Spot Advisor | Claude Advisor | second-opinion | PAL MCP | Evidence to collect |
| --- | --- | --- | --- | --- | --- |
| Quality | One checkable action from selected evidence | Advisor sees the executor transcript | Read-only blind review with verified findings | Scoped review and deep analysis | Independent final grades and discordant outcomes |
| Speed | One consultation per round | Server-side call within the request | Separate CLI review and reconciliation | Configurable model and depth | Elapsed time through independent grading and verified deliveries by deadline |
| Value | Bounded context and model attribution where reported | Executor and advisor usage reported separately | Existing CLI accounts can run the review | Model and depth can be selected by task | Whole-task tokens, frontier tokens and comparable API-equivalent cost per verified task |
| Usability | Codex subscription, Claude Code CLI and compatible gateway | Native Messages API tool | One command after installing and signing into both CLIs | MCP setup and multiple specialized tools | Time to first verified task and human interventions |
| Context control | Preview selected evidence before dispatch | Advisor receives the executor transcript | Counterpart reads the relevant repository | Caller scopes analysis by files or directories | Evidence sent and diagnostic omissions |
| Control and recovery | Session budget, revision checks and ambiguous-dispatch handling | Tool call limits and structured results | Bounded follow-up and reconciliation of findings | Per-tool model and analysis settings | Recovery outcomes, stale replies and duplicate generations in the same fault scenarios |

### Measure net savings with completed work

Use the [SWE-bench Pro V2 public benchmark](https://labs.scale.com/leaderboard/swe_bench_pro_public_v2) and the pinned upstream verifier from the [existing research protocol](docs/research-protocol.md). Freeze a fresh subset of eligible maintenance issues before running the comparison. Give every workflow the same assigned issues and grade its final patches with the same upstream tests. Report results as a named subset with its size, task IDs and budget. A workflow adapted from a review tool can use its normal review behavior, followed by the common executor applying any selected recommendations and submitting a patch. Count both steps in the timing and usage.

1. **Freeze the test before collecting results.** Choose a recurring benign repair failure, fresh eligible cases, run order, a common deadline, an acceptable pass-rate margin and a meaningful savings threshold. Use the same base revisions and independent verifier. Compare Spot Advisor with the three peers using their documented workflows. Include a cheaper executor alone and direct frontier execution as baselines. Match models and effort where supported. Record product-level differences where matching is unavailable.
2. **Isolate what the consultation contributes.** At the same saved failure checkpoint, compare the cheaper executor continuing alone, receiving one frontier reply to a generic question, receiving one reply to a focused question, and handing off to a frontier executor. Match remaining tools and time. Report equal-budget continuation results alongside the whole-task outcome. Keep the four-way checkpoint experiment distinct from the peer product comparison.
3. **Count the entire job.** For each arm, divide all observed executor and advisor input plus output tokens by independently verified completions. Include the shared prefix once per arm, rework, eligible runs that never consulted, failed tasks and retry usage. Show frontier tokens separately, including any takeover. Report cache treatment and the source of each usage receipt. Preserve missing usage as unknown and show whether it can reverse the ranking. Treat subscription charges and API-equivalent estimates according to how they were measured.
4. **Estimate the total model price, including caching.** For each model, price uncached input, cache reads, cache writes where separately billed, and output at their respective published API rates. For rates per million tokens, sum `tokens × rate` across those categories and divide by `1,000,000`. Normalize provider receipts before pricing so cached input included in an input total is counted only once. Show the measured cache-hit share for each model, including Luna Max. Where a receipt lacks a cache breakdown, mark that portion as unknown and show the estimate at ordinary input rates separately. Leave entirely missing usage visible as partial coverage. Report estimated dollars for the entire arm and per verified task, with rate sources and dates. The estimate covers model usage at public rates. Subscription fees and gateway markups are outside its scope.
5. **Show both sides of the result.** Give each workflow one row with eventual passes out of all assigned issues and passes by the same review deadline. Show pass rates per 100 assigned issues as a normalized view beside the raw counts. Put a stacked bar for frontier and other model tokens per verified task next to those counts. Add a breakdown by model and arm for uncached input, cache-read tokens, separately reported cache writes and output. Show both the absolute cache-read count and its share of input tokens alongside the number of requests with cache fields. Label the estimated total price, estimated price per verified task, time through grading and receipt coverage beside the bars. Export the frozen manifest, sanitized case-level receipts and analysis. Use a radar chart only once comparable measurements exist for the axes it displays.

Claim net token savings only if the paired quality result clears the prespecified margin and the whole-task token comparison supports a reduction on the fresh cases. A drop in frontier usage alone supports a narrower statement. Record null results and wins for another workflow.

### Paper extension for 2.2: when to ask and what to ask

The [current paper](paper/README.md) motivates this study with failed local verification on a patch that later passed independent grading. Its two workflows vary executor and advisor access together. The 2.2 paper should investigate the decision to consult and the contents of the question.

**When to ask.** Treat repeated failure as a signal to inspect the evidence. Before requesting advice, the executor should record that the intended check ran and that any named dependency or required fixture was available. It should identify a decision that affects the next action, cite the observation leaving it unresolved, and check whether a cheap local probe would distinguish the options. Continue locally while that probe is available. Consider one consultation when the remaining alternatives would lead to materially different actions and there is time to verify one. A compact checkpoint record should capture the check, revision, candidate actions, and reason for asking or continuing. These are candidate criteria to test.

**What to ask.** Give the advisor the goal, constraints, exact failed assertion or conflicting observations, what was tried, and one question that can change the next action. For example, ask which of two plausible causes best fits the observed output and which single check would distinguish them. Require one action and one way to verify it. If diagnosis remains uncertain, a discriminating check is a valid reply. Preserve the executor's responsibility for rerunning the check and grading the final patch.

**Evaluate the two decisions separately.** Compare the current repeated-check rule with the proposed evidence-based rule across the same fresh task cohort, retaining tasks on which neither policy calls for help. At eligible saved checkpoints, compare focused advice with local continuation and frontier takeover. Separately compare focused and generic advice on those same checkpoints. Hold supplied evidence, advisor model and budget fixed across the two question variants. Freeze the eligibility and scoring rules before looking at outcomes.

Report independently verified completions through grading, total and frontier tokens per verified task, estimated model cost, and human intervention where observed. Also report when a reply reversed a passing outcome, when a skipped consultation could have helped in the paired checkpoint test, and the number of screened tasks that reached an eligible checkpoint. Add the trigger, question template, experimental design, and observed results to the 2.2 manuscript. Keep the existing results reproducible from their frozen records.

### Baseline and iteration order

Freeze three fresh 2.2 reference arms before changing the default: Luna Max alone, Luna Max with the 2.1 consultation policy, and Astra alone. Pin the model IDs, effort, checkout, test images, tool access, and time limits. Evaluate the 2.2 candidate against all three on the same assignments. The 2.1 comparison measures the product iteration, Luna alone measures the value of adding advice, and Astra alone measures the trade-off against assigning the whole task to the frontier model.

Track the share of assigned tasks that submit a gradable artifact and the share that pass independent verification. The primary denominator for both is all assigned tasks. Count submissions through the deadline and retain model interruptions, failed attempts, and observed usage. For a baseline with verified completions and complete attributable usage, compute net token savings as `1 − (candidate total tokens per verified task / baseline total tokens per verified task)`. Apply the same calculation separately to frontier tokens and estimated dollars when the baseline denominator is positive. Show absolute totals and the pass counts beside the ratios. A zero-pass arm has no per-pass estimate.

### First multimodal study: mobile screenshot review

Start with an existing mobile sign-up page whose primary action competes with secondary elements. The executor owns the page and makes a focused edit. The advisor can inspect one screenshot to decide which visible element most distracts from the primary action. A fixed task goal and a reproducible render make this narrower than judging a whole site's aesthetic quality. [Design2Code](https://arxiv.org/abs/2403.03163) motivates using rendered screenshots and human evaluation together. Use an original local repair fixture for the pilot and report it as a separate visual cohort from SWE-bench Pro V2.

1. **Qualify the image route.** Render one fixture in a fixed mobile viewport with fonts and assets pinned. Use a small test screenshot containing a visual detail absent from the text prompt to verify that the chosen Astra route receives the image and returns the expected model identity where the provider reports it. Record image size, revision, latency and usage. The shipped structured v2 packet is text-only. The existing image-capable gateway path provides a starting point once the requested model and provider have been tested.
2. **Test a visual decision.** Give Luna the page, goal and local browser checks. Clear observable functional failures locally, such as an unclickable action or a clipped label. If the remaining decision is visual hierarchy, ask the advisor which visible element competes most with the main action and what one change would improve it. Bind the reply to the page revision and screenshot. Have Luna make the edit, rerender and rerun functional checks. Include an already-clear page to see whether the policy avoids needless review and edits.
3. **Measure the gain from seeing the image.** Fork the same saved page state into Luna alone, Luna with one text-only Astra reply, Luna with one Astra reply that also receives the screenshot, and Astra handling the same repair end to end from the common starting page. Keep the written brief and remaining allowances equal for the two advice arms. Grade clicks, overflow and readability constraints independently. Show screenshots in randomized order to reviewers blinded to the workflow, and measure whether they can identify the intended action on first view. Report review disagreement, harmful edits, time through verification, total and frontier tokens per verified task, and rough cache-aware cost.

Run a small disjoint pilot to validate the route and rubric before freezing the main visual task set. Include a Luna-Max-with-image baseline in the fresh cohort. Luna Max can read a screenshot on the tested subscription route, so the key comparison is whether Astra's judgment improves outcomes beyond what Luna can achieve with the same screenshot. Expand to reference-image prompting only after the screenshot study shows where one visual consultation improves the result at an acceptable cost.
